# Phase 0 Research: Inventory Dashboard Foundation & Guardrails

All unknowns from the Technical Context are resolved below. Each entry records the decision, the rationale, and the alternatives rejected.

## R1. Filament major version — v4 (docs) vs v5 (code)

- **Decision**: Target **Filament v5** and its v5 APIs.
- **Rationale**: `composer.json` pins `filament/filament: ~5.0`; recent commits state "upgrade Filament to v5.7" and "republish Filament v5 frontend assets"; installed docs resolve to `filament/filament@5.x`. Earlier "v4" text in CLAUDE.md, AGENTS.md, and `FILAMENT_INVENTORY_DASHBOARD_PLAN.md` was stale.
- **Alternatives rejected**: Following the "v4" text would produce APIs that don't match the installed framework.
- **Follow-up**: DONE (2026-07-22) — the stale "v4" references in CLAUDE.md, AGENTS.md, and the plan doc were corrected to v5.

## R2. Panel access gate mechanism

- **Decision**: Implement the gate on the `User` model via `canAccessPanel(Panel $panel): bool` using a `match` on `$panel->getId()`: `'admin' => $this->isAdmin()`, `default => false`.
- **Rationale**: Filament v5's documented panel-authorization contract is `FilamentUser::canAccessPanel()` (the model already implements `FilamentUser`). The committed model's own comment says role-based auth "will be layered on top of this gate once user roles are implemented" — FI-0 is that layering. Keeping the gate on the model (not middleware) matches Filament v5 convention and the existing scaffolding.
- **Fail closed for unknown panels (hardened after code review)**: the first implementation returned `true` for any panel id other than `'admin'`, reasoning that no other panel exists yet. A code review correctly flagged this as a latent authorization gap — a permissive default that would silently open a future second panel to every user unless someone remembered to extend this method. Changed to `default => false`: a new panel must explicitly opt in here. No behavior change today (only the `admin` panel is registered), but the failure mode for "someone forgets to update this" flips from open to closed.
- **Alternatives rejected**: Custom `authMiddleware` on the panel — redundant with the framework contract and harder to unit-test; a Gate/policy on the panel — not the idiomatic v5 mechanism for login eligibility; permissive default for unknown panels — rejected per the hardening above.

## R3. Identifying System Admins — the `user_type` primitive

- **Decision**: Introduce a backed string enum `App\Enums\UserType { Admin, Customer, Employee }` and add a `user_type` column to `users` (string, cast to the enum). FI-0 owns only this minimal primitive; full user management stays with the future `003-auth-users-spatie-access` spec.
- **Rationale**: The constitution mandates `users.user_type` as the channel identifier; no column exists yet. The gate (FR-001/FR-002) is impossible without it. A backed enum gives type safety and satisfies the 100% type-coverage gate.
- **Migration default (security)**: The column is NOT NULL with a **least-privilege** default of `'customer'`. Defaulting to `'admin'` was rejected as a privilege-escalation smell — any insert that omits `user_type` would silently become an administrator. The dedicated System Admin is created explicitly in `DatabaseSeeder`.
- **Factory default (test convenience)**: `UserFactory::definition()` sets `user_type => UserType::Admin`, because the application currently exposes only the admin panel and every existing test assumes its factory user can reach `/admin`. This keeps the existing `DashboardPageTest` valid **without edits** (see R8) while denial paths use explicit `customer()` / `employee()` states. The factory default (admin, test-only) and the DB default (customer, secure) are intentionally different: defense-in-depth at the database, convenience in tests.
- **Alternatives rejected**: A boolean `is_admin` — cannot represent Customer/Employee channels the constitution requires; a roles-only check without `user_type` — contradicts the constitution's explicit channel model and couples panel eligibility to role seeding order.
- **Coordination**: Recorded in plan Complexity Tracking. The auth spec extends (adds Customer/Employee flows, validation, management UI) rather than replaces this enum/column.

## R4. Granular permission catalogue and seeding

- **Decision**: Define the canonical `inventory.*` permission strings in one place (`App\Enums\InventoryPermission`) and seed them idempotently via `InventoryPermissionSeeder` using Spatie Laravel Permission. The enum lives under `App\Enums` — not a separate `App\Support` namespace — because the repository's Pest `arch()` Laravel preset asserts `App` classes are not enums except under `App\Enums` (discovered when the preset failed against the originally planned `App\Support\Inventory\InventoryPermission` location). Catalogue (from spec FR-003 / plan §2.3): `inventory.warehouse.view`, `inventory.warehouse.manage`, `inventory.stock.view`, `inventory.movement.view`, `inventory.adjustment.view`, `inventory.adjustment.create`, `inventory.adjustment.confirm`, `inventory.transfer.view`, `inventory.transfer.create`, `inventory.transfer.confirm`, `inventory.reservation.view`, `inventory.reservation.release`, `inventory.export`.
- **Rationale**: Principle IV mandates Spatie. A single source prevents drift between seeder and policies. Idempotent seeding (`firstOrCreate`) lets the seeder run repeatedly and in tests.
- **Alternatives rejected**: Hard-coding strings in each policy — invites typos and drift; a config file — an enum/const class is more type-safe and testable and matches the codebase's enum-heavy style.
- **Guard**: Permissions use the default `web` guard (the panel is session/web-authenticated).

## R5. Reusable authorization/policy pattern

- **Decision**: Provide `App\Policies\Concerns\ChecksInventoryPermissions`, a trait exposing `authorizeInventoryAbility(User $user, string $ability): bool`, which looks up `$ability` in an `inventoryPermissionMap(): array<string,string>` that each consuming policy implements (ability => `inventory.*` permission name), then checks `$user->can($permission)`. An ability absent from the map is denied by default. FI-1+ resource policies implement the map and delegate their `viewAny`/`view`/`create`/`update`/`delete`/`confirm`/`release`/`export` methods to this helper; no resource policy is created in FI-0 (no models yet).
- **Rationale**: Filament v5 reads Laravel policies automatically for resource CRUD and supports `authorize()` for custom actions. Centralizing the ability→permission lookup keeps authorization identical to the API surface (Principle IV, plan §2.3) and avoids forking. Deny-by-default for unmapped abilities is how "no delete on ledgers" (FR-011) is realized without a special case.
- **Alternatives rejected**: A single generic method that *derives* the permission name from the ability and a guessed resource key (e.g. string-interpolating `inventory.{$resource}.{$ability}`) — rejected because the actual catalogue is not uniform: `stock`/`movement` have only `.view` (no create/confirm at all), `release` and `export` are not per-resource permissions, and `manage` (not `create`) is warehouse's write permission. An explicit per-policy map is honest about this instead of papering over it with string-guessing. Per-resource ad-hoc `can()` calls — duplication and drift. Filament Shield plugin — adds an unapproved dependency (CLAUDE.md forbids changing dependencies without approval).

## R6. Action → domain-service adapter

- **Decision**: Provide `App\Filament\Concerns\InteractsWithInventoryServices`, a trait exposing a helper (`runInventoryOperation(callable $operation, string $successMessageKey): void`) that invokes the operation, catches `DomainException` and `Illuminate\Validation\ValidationException`, and emits a Filament success/danger `Notification` accordingly — performing no writes itself.
- **Rationale**: Plan §2.1 mandates Filament actions be thin adapters over services. Encapsulating the try/translate/notify pattern once keeps every future action consistent and lets FI-0 unit-test the behavior with a fake operation before any real service exists.
- **Alternatives rejected**: Repeating try/catch in each action — violates DRY and is untestable in isolation; swallowing exceptions silently — violates FR-007 (errors must surface).
- **Testability**: Unit-tested by passing (a) a no-op closure → success notification asserted, (b) a closure throwing `DomainException` → danger notification asserted and no state mutated.

## R7. Enforcing "no direct stock writes" — architecture test

- **Decision**: Add a Pest `arch()` expectation asserting that classes in the `App\Filament` namespace do **not** use the inventory write models (`App\Models\InventoryStock`, `App\Models\InventoryMovement`). Extend `tests/Unit/ArchTest.php`.
- **Rationale**: SC-004 requires an automated build-failing check. Pest arch expresses namespace-usage constraints declaratively.
- **Alternatives rejected**: A runtime test — cannot prove absence across all code paths; a manual review checklist — not build-enforced, fails SC-004's "fails the build" requirement.
- **Verified behavior (empirically checked during implementation)**: the expectation passes today with the target classes referenced only as string literals — it does **not** currently error just because those classes don't exist. Whether it *actively catches* a violation was verified directly: a temporary stub `App\Models\InventoryStock` class plus a temporary `App\Filament\Concerns` trait referencing it was added, confirmed the guard **failed** (`Expecting 'App\Filament' not to use 'App\Models\InventoryStock'`), then both temporary files were removed and the suite reconfirmed green. So the guard is genuinely forward-active: no test edit is needed when the real inventory models land in FI-1+; the first Filament class to import one will fail the build immediately.

## R8. Existing test reconciliation (DashboardPageTest)

- **Decision**: Leave `DashboardPageTest` **unchanged**. Because `UserFactory` defaults `user_type` to `Admin` (R3), its `User::factory()->create()` users still satisfy the new gate and continue to reach `/admin`. Denial is covered by new cases in `PanelAccessTest` (customer/employee/guest) using explicit factory states.
- **Rationale**: Keeping the factory default aligned with the existing tests' assumption is the lowest-churn, most reviewable change (CLAUDE.md "small, reviewable changes"), and avoids touching passing tests. The gate is still meaningfully proven by the explicit allow + denial cases in `PanelAccessTest`.
- **Alternatives rejected**: Defaulting the factory to a non-admin and editing every existing dashboard test to `->admin()` — larger diff across passing tests for no behavioral benefit.

## R9. Internationalization scope

- **Decision**: Add English keys for permission labels and adapter notification messages to `lang/en/admin.php`. Do **not** restore `lang/ar/admin.php` in FI-0.
- **Rationale**: The spec's functional requirements do not include Arabic; Arabic restoration is cross-cutting (plan §2.7, Open Question #8) and spans every phase's keys. Bundling it here would exceed FI-0 scope and the "small, reviewable change" rule.
- **Alternatives rejected**: Restoring `lang/ar` now — scope creep; skipping label keys entirely — permissions/notifications need human-readable labels.

## R10. Database engine

- **Decision**: Treat the engine as unconfirmed; write the `user_type` migration with engine-agnostic Blueprint methods (`string()->default('customer')`, per R3) and rely on SQLite for local tests (as the repo already does).
- **Rationale**: PRD §11 / Open Question #6 leaves MySQL vs PostgreSQL open; Filament and Eloquent migrations are engine-agnostic for this simple column. Locking the engine is out of FI-0 scope.
- **Alternatives rejected**: Engine-specific column types (e.g. native enum) — reduces portability and complicates the future engine decision.

## R11. PHPStan findings discovered during implementation

- **Fixed — Larastan `casts()` method parsing was disabled by default.** `phpstan.neon` did not set `parseModelCastsMethod: true`, so Larastan (level `max`) could not read the `User::casts()` method's return type and treated `$this->user_type` as a plain `string`. This produced a real, correct finding (`identical.alwaysFalse` on `$this->user_type === UserType::Admin` in `isAdmin()`) — not a false positive. **Fix**: added `parameters.parseModelCastsMethod: true` to `phpstan.neon`. This is a pre-existing project-level PHPStan config gap (predates FI-0) that FI-0's `isAdmin()` happened to be the first code to expose, because it's the first strict enum comparison against a `casts()`-declared attribute. No baseline entry or ignore was used — the underlying config was corrected.
- **Resolved — `trait.unused`.** PHPStan (level `max`) reported `App\Filament\Concerns\InteractsWithInventoryServices` and `App\Policies\Concerns\ChecksInventoryPermissions` as "used zero times and is not analysed." PHPStan's own documentation (the `trait.unused` tip link) confirms it does not analyse a trait in isolation — only as part of a class that uses it. Both traits are intentionally consumer-less **in production code** for FI-0: they are reusable foundation building blocks (FR-012) that FI-1+ resource policies and Filament actions will consume once those resources exist (no models yet — Open Question #11).
  - **Dead end explored and rejected — convert trait to abstract class.** Laravel policies have no required base class, so `ChecksInventoryPermissions` could in principle become an abstract `InventoryPolicy` base class instead of a trait — abstract classes are analysed by PHPStan on their own, with no `trait.unused`-style limitation. This was implemented and verified to resolve the PHPStan finding, **but it violates this project's own Pest `arch()` Strict preset**, which asserts for every namespace: `not->toBeAbstract()`, `not->toHaveProtectedMethods()`, and `toBeFinal()`. Both traits rely on an abstract method contract plus a protected helper method — exactly the shape the Strict preset reserves traits for (traits are the only construct in this codebase exempt from those three rules). The conversion was reverted; `InteractsWithInventoryServices` has the same constraint plus an independent one — Filament pages/actions already extend Filament's own base classes, so composition *must* be a trait (single inheritance), not a base class, regardless of the PHPStan finding.
  - **Actual fix — give PHPStan a real consumer by including the FI-0 unit test fixtures in its analysed paths.** `phpstan.neon`'s `paths` accepts individual files, not just directories. `tests/Unit/ChecksInventoryPermissionsTest.php` and `tests/Unit/InteractsWithInventoryServicesTest.php` already contain genuine `use TraitX;` consumers (anonymous classes built specifically to exercise each trait) — they were just outside PHPStan's analysed paths. Adding exactly those two files to `paths` makes PHPStan analyse the traits for real, because they now *are* really used, with no suppression of any kind. This is not "designed to make a check pass" — the consumers already existed for testing purposes; only PHPStan's visibility into them changed.
  - **Consequence — the two test files were retyped for real, not just to dodge errors.** Adding them to PHPStan's paths surfaced 24 unrelated findings (untyped `array` parameters, an `object`-typed helper return with an undefined method call, `mixed` offset access into `session('filament.notifications')`). Fixed each at the root: a local `array<string, string>` PHPDoc on the map parameter/return; a small test-local interface (`InventoryPolicyStub` / `InventoryOperationRunner`) giving the anonymous class's return a concrete, checkable type instead of bare `object`; and — for the notification assertions — switched from indexing the raw `session('filament.notifications')` array to Filament's own `Notification::assertNotified(Notification::make()->...)` testing helper (`filament/notifications` `Testing/helpers.php`), which is the framework-sanctioned way to assert a notification was sent and avoids `mixed` array access entirely. No `@phpstan-ignore`, no `@var` override, no baseline entry, no type-widening.
- **Verification performed**: `composer test:types` → 0 errors. Full `composer test` chain green end-to-end (pint, rector, phpstan, 100% type coverage, 62/62 tests, 100% code coverage). Both traits remain fully self-contained (no external abstract-method dependency crossing into unanalysed territory), so there was no hidden type-safety risk being masked by the original finding.
