# Phase 0 Research: Support and Maintenance Dashboard

**Feature**: `016-support-maintenance-dashboard` | **Date**: 2026-08-13

Every item below was an open technical unknown after `/speckit-clarify`. Each is
resolved by direct inspection of this codebase's existing conventions (cited by
file path), not by generic best practice, per Constitution Principle II
(reuse existing domain-service/Filament conventions) and the ADR 0004
instruction to route every mutation through `app/Services/Support/` using
existing infrastructure.

## 1. Ticket numbering

**Decision**: `TCK-000001` format — a fixed `TCK-` prefix plus a zero-padded
6-digit sequence, generated by a private `nextTicketNumber(): string` method
inside the creating service, called from inside the enclosing
`DB::transaction(..., attempts: 5)`.

**Rationale**: Every existing numbered document in this codebase
(`Order::order_number` → `SO-######`, `InventoryAdjustment::adjustment_number`
→ `ADJ-######`, `StockTransfer::transfer_number` → `TRF-######`,
`InventoryOperation::operation_number` → `OP-######`) uses the identical
mechanism: `Model::query()->whereNotNull($column)->lockForUpdate()->max($column)`,
parse the numeric suffix with `mb_substr($max, $prefixLength) + 1` (or `1` when
none exist), `sprintf('%s-%06d', $prefix, $next)`. Concurrency safety is two
layers, not one — the locking read serializes concurrent transactions
computing the "next" number, and a DB `unique()` constraint on the column is
the backstop if that's ever bypassed, with `DB::transaction(attempts: 5)`
retrying the whole block on that failure. This satisfies SC-001 (guaranteed
uniqueness under concurrent creation) with zero new infrastructure.
See `app/Services/Orders/OrderFulfillmentService.php::nextOrderNumber()`.

**Alternatives considered**: A dedicated `ticket_number_sequences` counter
table — rejected, no existing numbered document in this codebase uses one,
and introducing one here would be a second numbering mechanism, which
Principle II (reuse, don't parallel-build) forbids without a proven need.
Date-embedded formats (`TCK-2026-000123`) — rejected, no existing document
number in this codebase embeds a date; `TCK-000001` matches the sibling
formats exactly.

## 2. Spare-parts consumption → Inventory integration

**Decision**: Call `App\Services\Inventory\InventoryBalanceService::transferOut(
$productVariantId, $warehouseId, $quantity)` to decrement stock (it locks the
`inventory_stocks` row via `lockForUpdate()` and throws `DomainException` if
`available_quantity` is insufficient), then in the same transaction
`InventoryMovement::query()->forceCreate([..., 'movement_type' =>
MovementType::ServiceConsumption, 'source_type' => 'service_record_part',
'source_id' => $part->getKey()])`. Reversal calls the mirror method,
`InventoryBalanceService::transferIn($productVariantId, $warehouseId,
$quantity)`, plus a second `InventoryMovement` row with the same `source_type`/
`source_id` and a positive quantity, linked back via
`service_record_parts.reversal_movement_id`.

**Rationale**: This is exactly the shape every existing Inventory service uses
(`StockTransferService::recordMovement()`, `InventoryAdjustmentService`,
`InventoryDamageService`) — `source_type`/`source_id` is a plain string+bigint
pair (not an Eloquent `morphTo()`), populated directly by the caller; no
central "movement source registry" exists to register with. `MovementType` is
a fixed backed enum with 9 existing cases, none of which mean "consumed for
service work," so one new case, `ServiceConsumption = 'service_consumption'`,
is added — a one-line enum change, not a new mechanism. Availability
pre-checks (for form-level feedback before submission) reuse
`InventoryOperationService::availableQuantity($productVariantId,
$warehouseId): ?float` rather than querying `InventoryStock` directly. This
satisfies FR-081 ("exactly one inventory movement... through the existing
Inventory services") and Constitution Principle III (stock source of truth is
`product_variant_id + warehouse_id`, every stock change creates a movement)
without any parallel stock-writing path.

**Alternatives considered**: Writing to `inventory_stocks` directly from a new
Support service — rejected outright, forbidden by Principle III and ADR 0004
("this module never writes stock directly"). Adding a `source` polymorph
relation to `InventoryMovement` — rejected as unrelated scope; every existing
caller already works with the plain string/bigint pair, and changing that
column's shape is a cross-cutting Inventory-module change no other spec asked
for.

## 3. Ticket attachments — Media Library, no bespoke table

**Decision**: `Ticket` implements `HasMedia`/`InteractsWithMedia` and
registers a private-disk `'ticket-attachments'` collection
(`$this->addMediaCollection('ticket-attachments')->useDisk('local')`), exactly
like `CustomerVisit::registerMediaCollections()` registers
`'visit-attachments'`. A plain Filament `FileUpload` field (this project has
no Spatie Media Library Filament plugin installed) writes to a scratch path,
and a new `TicketAttachmentSynchronizer` service (modeled on
`ProductMediaSynchronizer`/`ShipmentAttachmentSynchronizer`) moves it into the
real collection via `addMediaFromDisk(...)->toMediaCollection(...)`. Serving a
file goes through a new signed `TicketMediaController` calling
`Gate::authorize('view', $ticket)` before streaming, mirroring
`VisitMediaController`.

**Rationale**: ADR 0004 explicitly overrides a literal reading of the ERD here
("Ticket attachments use Media Library collections, not the custom
`ticket_attachments` file table... consistent with how ADR 0003 handled visit
attachments and voice-note audio"), and FR-103/FR-104 forbid a feature-specific
file table. No `ticket_attachments` migration is created.

**Alternatives considered**: `filament/spatie-laravel-media-library-plugin` —
not installed in this project (`composer.json` has no such package, no
`SpatieMediaLibraryFileUpload` usage anywhere), so introducing it now would be
a dependency change requiring separate approval per `AGENTS.md`/CLAUDE.md
("do not change the application's dependencies without approval"); the plain
`FileUpload` + synchronizer pattern is what every other module already uses,
so it is reused rather than requesting a new dependency for one feature.

## 4. RBAC: new roles, new permission catalogue, self-checking services

**Decision**: Add `SupportManager = 'Support Manager'` and `SupportAgent =
'Support Agent'` cases to `App\Enums\DashboardRole` (the single
`fixedRoleNames()` source of truth every module's `isAdmin()`-bypass check
consults). Add `App\Enums\SupportPermission` — a dot-namespaced
`support.{resource}.{verb}` catalogue with a `values(): array` static method
and **no** `fixedRoleNames()` method of its own (the stale, dead copy on
`CrmPermission` is a documented mistake predating `DashboardRole`, not a
pattern to repeat). Add `database/seeders/SupportPermissionSeeder.php`
mirroring `EmployeePermissionSeeder`'s create-permissions-then-grant-per-role
shape, granting `System Admin` everything and `Reviewer` a view-only subset
(both role names are reused, not redefined, across every module's seeder).
Add `app/Policies/Concerns/ChecksSupportPermissions.php` modeled on
`ChecksEmployeePermissions` (the newest, most deliberate version — the
`isAdmin() && ! hasAnyRole(DashboardRole::fixedRoleNames())` bypass, not
`ChecksInventoryPermissions`'s older no-bypass version).

Every `app/Services/Support/*` domain service that mutates state
**self-checks** authorization (`$user->can(...)` or
`Gate::forUser($actor)->authorize(...)`) in addition to the Filament layer's
own `->authorize()` call on each Action/BulkAction.

**Rationale**: Filament's own page-open authorization (`canViewAny`/`canEdit`/
etc., auto-resolved against the model's policy — no override needed once the
policy exists) and each Action's `->authorize('ability')` call already satisfy
"checked when a page is opened and when an action is executed" for the
*dashboard* entry point. But spec 016 (FR-005/FR-006/FR-008, User Story 1
scenario 5, and Edge Case "an unauthorized direct service call that bypasses a
hidden or disabled UI control is rejected exactly as the equivalent UI action
would be") explicitly requires the *same* rejection for a direct service call
that never goes through Filament at all. Investigating the Employees module
found this guarantee is **not** uniform there today —
`EmployeeAccessService` has zero internal check and trusts Filament entirely,
while `EmployeeReportService` and `DashboardRoleAssignmentService` do
self-check because they have more than one entry point. Support must follow
the stricter pattern (self-checking) everywhere, since a domain service
invoked directly (as in a test, or a future non-Filament entry point) must
never be an authorization bypass. This is a deliberate, spec-driven
improvement over the weaker precedent, not an inconsistency with it.

**Alternatives considered**: A single shared `SupportAuthorizer` gate class
called from every service — rejected as an unnecessary abstraction; every
existing self-checking service (`EmployeeReportService`,
`DashboardRoleAssignmentService`) just calls `$user->can()`/`Gate::authorize()`
directly, and three lines of repeated self-check per service is well under
the threshold where a shared helper earns its keep.

## 5. Audit trail

**Decision**: Every sensitive mutation calls Spatie's `activity()` helper
directly from inside the same transaction as the write it audits:
`activity()->performedOn($ticket)->causedBy($actor)->withChanges(['old' =>
[...], 'attributes' => [...]])->withProperties(['source_channel' =>
'dashboard', 'ip_address' => request()->ip()])->log('support.ticket.status_changed')`.
Action strings are lowercase, dot-namespaced `support.{entity}.{past-tense-verb}`
(`support.ticket.created`, `support.ticket.assigned`,
`support.payment_link.settled`, `support.maintenance_record.status_changed`,
`support.service_record_part.consumed`, `support.service_record_part.reversed`,
...).

**Rationale**: This is the exact, unvarying shape used at every existing call
site (`InventoryAdjustmentService::confirm()`,
`InventoryDamageService::execute()`, `StockTransferService::dispatch()`), per
ADR 0005 which replaced the deleted bespoke `App\Services\Audit\AuditLogger`
with this helper. `withChanges(['old' => ..., 'attributes' => ...])` is a real
native method on Spatie's `ActivityLogger`; the `old`/`attributes` key
convention and the fixed `source_channel`/`ip_address` properties pair are
this project's standardized shape, not ad hoc per-call formatting. No wrapper
trait exists anywhere in the codebase to call instead — this satisfies
FR-104's corrected wording (the audit trail is the shared `activity()`-based
infrastructure, not the deleted `AuditLogger` class) with zero new code.

**Alternatives considered**: None — this is a settled, singular convention
with no variation across five-plus existing call sites; there is nothing to
weigh against.

## 6. SLA clock semantics and defaults (from `/speckit-clarify`)

**Decision**: Continuous 24/7 calendar time. `response_due_at` /
`resolution_due_at` are computed as `live_at + target_minutes`, with only the
`waiting_customer` pause (accumulated-seconds counter, FR-055) suspending the
resolution clock — no business-hours or holiday calendar is introduced.
Default seeded targets: Urgent 1h response / 4h resolution; High 4h / 24h;
Normal 8h / 48h; Low 24h / 72h, editable per-priority by a Support Manager
(FR-051) but never retroactive to an already-started ticket (FR-053).

**Rationale**: Resolved interactively during `/speckit-clarify` (2026-08-13
session, recorded in `spec.md` §Clarifications) — no business-hours/holiday
calendar concept exists anywhere else in this codebase, and the Owner
Decisions (D3) frame SLA as "added on top of the ERD baseline," not as a
request for new scheduling infrastructure. Continuous-time arithmetic keeps
the engine a pure timestamp calculator (`live_at + minutes`, minus paused
seconds), independently unit-testable with no calendar dependency.

**Alternatives considered**: Business-hours-aware clock — rejected by the
user during clarification; would require designing and seeding a new
business-hours/holiday-calendar concept with no existing precedent or
documented requirement anywhere in `Docs/PRD.md`, `Docs/SDD.md`, or
`Docs/database/ERD.md` (confirmed absent by direct search).

## 7. Spare-parts reversal granularity (from `/speckit-clarify`)

**Decision**: Full-quantity reversal only. `service_record_parts` gains
`reversed_at`, `reversed_by_user_id`, and `reversal_movement_id` (nullable) on
the *original* consumption row rather than a separate reversal-ledger table; a
correction to a smaller amount is a full reversal followed by a new, smaller
consumption row.

**Rationale**: Resolved interactively during `/speckit-clarify` — keeps
exactly one compensating movement offsetting exactly one original movement,
the simplest shape to audit, and matches FR-086's framing of reversing *a*
consumption (singular), not a sub-quantity of one.

**Alternatives considered**: Partial reversal with a remaining/reversed split
column — rejected by the user during clarification as unnecessary bookkeeping
complexity for a System-Admin-only, rare corrective action.
