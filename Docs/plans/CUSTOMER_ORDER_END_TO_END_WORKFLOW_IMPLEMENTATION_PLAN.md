# Customer Order End-to-End Workflow Implementation Plan

**Project:** IERP  
**Target baseline:** current `dev` branch as inspected on 2026-09-14  
**Primary modules:** Sales → Logistics/Inventory → Purchasing → Accounting/Payments → Support/Warranty  
**Related plan:** `Docs/plans/PURCHASE_ORDER_END_TO_END_WORKFLOW_IMPLEMENTATION_PLAN.md`  
**Plan type:** implementation plan only; this document changes no production behavior by itself.

## 1. Goal

Redesign the Customer Order / Sales Order flow so one business order can be understood end-to-end without making `Order` a cross-module god object and without requiring one employee to execute work in another module.

The target business flow is:

```text
Sales
Customer Order Draft
    → Confirmed
    → Released

Logistics
    → Warehouse Allocation
    → Reservation / Preparation
    → Dispatch
    → Shipment In Transit
    → Shipment Arrived

Accounting
    → Invoice
    → Payment

Exceptions
    → Procurement Requirement when stock is short
    → Customer Return
    → Credit Note / Refund
```

The final user experience must answer, from the Customer Order workspace:

1. What did the customer order?
2. What was commercially confirmed?
3. What quantity is allocated to warehouses?
4. What is reserved and ready to dispatch?
5. What has physically left inventory?
6. What has arrived to the customer?
7. What quantity is blocked by stock shortage or procurement?
8. What has been invoiced, paid, credited, returned or refunded?
9. What is the current blocker?
10. Which module owns the next action?

The implementation must preserve the existing canonical Inventory, Invoice, Payment, Customer Return and Credit Note engines rather than duplicating their truth inside `orders`.

---

## 2. Non-negotiable architecture rules

1. `Order` remains the commercial customer commitment.
2. Sales owns customer, products, UOM, quantities, prices, tax, payment terms, requested delivery information and commercial lifecycle.
3. Sales Order creation must not select warehouses, lots, serials, reservations or shipment tracking.
4. Logistics owns warehouse selection, warehouse splits, lots/serials, reservation, delivery execution and shipment handling.
5. Purchasing owns supplier selection, Purchase Orders and supplier confirmation. Sales must not execute Purchasing actions from the Customer Order screen.
6. Accounting owns Invoice issue/posting, receivables, Payments, Credit Notes and Refunds.
7. Inventory on-hand changes only through canonical Inventory posting/operation services.
8. Draft, Confirm, Release, warehouse planning and reservation must not change on-hand stock.
9. A customer Delivery reduces stock only when the Delivery `InventoryOperation` is completed by Inventory/Logistics.
10. A Shipment must not be `In Transit` before the associated Delivery has physically left warehouse stock.
11. Do not duplicate stock, reservation, invoice balance, payment or return facts on `orders` merely to simplify the UI.
12. Do not expand `Order.status` into a combined Sales + Inventory + Shipment + Accounting state machine.
13. Cross-module facts may be visible in a workspace, but the action must still be authorized and executed by the owning module/service.
14. `DeliveryNoteResource` may remain a Sales read-only evidence surface; it must not become a second Logistics execution surface.
15. Existing pricing provenance on `OrderLine` must remain immutable once the commercial order is confirmed.
16. Existing delivery-line → order-line provenance must remain intact for multi-UOM orders.
17. Existing Invoice delivery provenance, Customer Return provenance and Credit Note provenance must remain intact.
18. Partial fulfillment across multiple deliveries and warehouses is a first-class requirement.
19. A stock shortage must not force Sales to choose a supplier or receiving warehouse.
20. The PO workflow from the Purchase Order plan remains canonical for procurement generated by a Customer Order shortage.

## 3. Current baseline found in the repository

### 3.1 Existing strengths to preserve

The current repository already contains strong domain pieces:

- `Order` owns commercial lines and relates to Deliveries, Shipments, Invoices, Procurement Requirements and legacy supplier confirmations.
- `OrderLine` already stores transaction UOM, base quantity, commercial price and immutable pricing provenance.
- Direct-order pricing is resolved by `DirectOrderLinePricingService` through `OrderLineObserver`.
- Quotation conversion preserves accepted quotation price/UOM/provenance and creates one commercial `Order`.
- `OrderFulfillmentService` can suggest warehouse splits, select batch/serial inventory, create Delivery operations and preserve `order_line_id` provenance.
- `InventoryOperationService::markReady()` reserves outbound stock without changing on-hand.
- `InventoryOperationService::complete()` is the canonical stock-changing transition for a Delivery.
- `InventoryOperationPolicy` already separates Delivery view/create/confirm permissions.
- `InvoiceService::createFromDeliveries()` requires completed Deliveries and prevents double invoicing of the same Delivery through delivery links.
- Consolidated invoicing across multiple completed Deliveries already exists.
- Payments are independent documents allocated to Invoices.
- Customer returns require completed customer Delivery evidence and prevent over-return.
- Credit Notes can link both Invoice lines and posted Inventory Return lines and prevent over-credit.
- Shipment arrival confirmation already supports Admin, Customer and System sources.
- Warranty activation already occurs from Shipment arrival confirmation.
- `DeliveryNoteResource` is read-only and scoped to Delivery `InventoryOperation`s.

### 3.2 Current problems to remove

The current flow mixes module ownership:

- `CreateOrder` asks Sales to select warehouses.
- `CreateOrder` asks for batches/lots and shipment data before the commercial Order exists.
- `OrderFulfillmentService::create()` creates the commercial Order and Logistics execution in the same transaction.
- `OrderPolicy::create()` currently requires `InventoryPermission::DeliveryCreate`, not a Sales Order permission.
- Quotation conversion immediately writes `status = ready` even though Logistics has not necessarily planned fulfillment.
- `Order.status = ready` is used as both commercial and operational meaning.
- `prepareExisting()` refuses a second fulfillment when any active Delivery or Shipment already exists, blocking true partial fulfillment.
- `productsForOrder()` returns the full ordered demand rather than the remaining uncommitted demand.
- `createDeliveries()` initializes remaining commercial quantity from the full Order lines and therefore is not designed for repeated partial fulfillment.
- `createDeliveries()` creates a Shipment with `status = in_transit` immediately after `markReady()`, while stock is only reserved and has not left the warehouse.
- Shipment status currently has only `in_transit` and `arrived`.
- Customer Order actions currently include `Request supplier confirmation` and `Create purchase order`.
- `Create purchase order` asks Sales for a receiving warehouse, conflicting with the new PO architecture where warehouse allocation is post-acceptance and Logistics-owned.
- `SalesProcurementService` currently performs supplier confirmation and PO creation from the Sales Order context.
- `OrderInfolist` shows useful raw sections but does not provide one derived business milestone, blocker, Next Action or unified quantity progress view.
- `OrdersTable` does not expose fulfillment progress, procurement blockers or next-action ownership.

## 5. Target Customer Order commercial lifecycle

Introduce a canonical `OrderStatus` enum and keep it deliberately small:

```text
Draft
  ↓
Confirmed
  ↓
Released
  ↓
Closed

Alternative terminal:
Cancelled
```

### 5.1 Meaning

**Draft**
- Sales may edit commercial data and lines.
- No Logistics execution is created.
- No reservation or stock movement.

**Confirmed**
- Customer-facing commercial facts are frozen.
- Quantity, UOM, price and price provenance are no longer editable through generic CRUD.
- Logistics still has no obligation until release.

**Released**
- The Order is handed to Logistics as fulfillment demand.
- Release itself creates no Delivery, reservation or stock movement.
- Procurement blockers are derived from uncovered fulfillment demand.

**Closed**
- No further normal fulfillment is expected.
- Can represent complete fulfillment or an explicitly short-closed remainder.
- Financial documents may remain open according to payment terms; do not overload commercial close with Payment status.

**Cancelled**
- Allowed only when no physical customer Delivery has been completed.
- If Logistics execution already exists, cancellation must first resolve/cancel the Logistics records according to Inventory ownership.

### 5.2 Do not persist these as `Order.status`

Expose these as derived workflow milestones instead:

```text
Awaiting Logistics Allocation
Partially Allocated
Awaiting Stock
Procurement In Progress
Reserved
Ready to Dispatch
Partially Dispatched
In Transit
Partially Delivered
Delivered
Partially Invoiced
Invoice Pending
Partially Paid
Paid
Return In Progress
Credit Pending
Refund Pending
Completed
```

These states are projections from domain evidence, not another database state machine.

## 6. Target end-to-end user flows

### 6.1 Direct Customer Order

```text
Sales
Create Draft
→ Customer + delivery address
→ Products/UOM/quantities
→ Pricing/tax/payment terms
→ Requested delivery date
→ Review
→ Confirm
→ Release

Logistics
Released Order appears in Outbound queue
→ Review availability
→ Suggest / adjust warehouse split
→ Assign lots / serials
→ Create Planned Deliveries
→ Reserve / Prepare
→ Dispatch

Inventory
Dispatch completes Delivery operation
→ Stock decreases

Shipment
Planned → In Transit → Arrived
→ Warranty activation on Arrived

Accounting
Completed Delivery becomes invoice-eligible
→ Invoice
→ Payment
```

### 6.2 Quotation conversion

```text
Accepted Quotation
→ Convert to Customer Order
→ Order starts Confirmed
→ Sales reviews requested delivery data
→ Release
→ same Logistics flow as direct Order
```

Quotation conversion must never bypass the common released-order Logistics flow.

### 6.3 Partial fulfillment

```text
Ordered: 100
Available: 60

Delivery A: 40 from Warehouse 1
Delivery B: 20 from Warehouse 2
Uncovered: 40

Dispatch 60
Remaining commercial demand: 40
Procurement requirement: 40

Purchased stock later received
→ Outbound queue becomes actionable again
→ Delivery C: 40
```

A previous Delivery must not block another fulfillment cycle for the remaining quantity.

### 6.4 Customer-order-driven procurement

```text
Released Customer Order
→ Logistics cannot cover part of remaining demand
→ Procurement Requirement created/synchronized
→ Purchasing queue
→ Purchasing chooses supplier
→ PO Draft (no receiving warehouse)
→ PO submit/approve/Accepted
→ Supplier confirmation according to PO plan
→ Logistics inbound allocation
→ Receipt completed
→ Procurement Requirement fulfilled
→ Customer Order Outbound queue becomes actionable
```

Sales sees progress but does not perform Purchasing actions.

### 6.5 Customer return

```text
Arrived customer Shipment / completed Delivery evidence
→ Customer Return initiated
→ Logistics receives/inspects returned goods
→ Inventory Return posted
→ Stock consequence recorded
→ Accounting sees Credit required
→ Credit Note
→ Refund / account-credit resolution
```

A delivery refusal / return-to-sender before customer arrival is a Logistics delivery exception, not a normal Customer Return.


```php

```

## 8.2 Add lifecycle evidence

Forward-only migration on `orders`:

- nullable `confirmed_at`
- nullable `released_at`
- nullable `closed_at`
- nullable `cancelled_at`
- index `(status, scheduled_at)`

Use activity log for actor/reason evidence unless a later requirement proves actor columns are necessary.

## 8.3 Add short-close quantity evidence

To support intentional under-fulfillment without corrupting ordered quantity, add to `order_lines`:

- `short_closed_base_quantity decimal(20,6) default 0`

Rules:

```text
0 <= short_closed_base_quantity
short_closed_base_quantity <= ordered_base_quantity - non_cancelled_fulfillment_quantity
```

Do not modify `base_quantity` or original commercial quantity to represent a short close.

## 8.4 New commercial service

Create:

- `app/Services/Sales/SalesOrderService.php`

Responsibilities:

```php
createDraft(User $actor, array $attributes, array $lines): Order
updateDraft(User $actor, Order $order, array $attributes, array $lines): Order
confirm(User $actor, Order $order): Order
release(User $actor, Order $order): Order
shortClose(User $actor, Order $order, array $lineQuantities, string $reason): Order
close(User $actor, Order $order, ?string $reason = null): Order
cancel(User $actor, Order $order, string $reason): Order
```

The service must lock the Order and lines for state transitions.

## 8.5 Commercial transition rules

### Draft → Confirmed

Validate:

- active customer;
- at least one line;
- positive normalized quantity;
- valid UOM snapshot;
- price/tax/provenance present;
- delivery address when required by delivery type;
- valid payment term if supplied.

No Inventory write is allowed.

### Confirmed → Released

Validate commercial completeness only.

Release must:

- set `released_at`;
- activity-log `sales.order.released`;
- emit an after-commit `SalesOrderReleased` event for notifications/projection refresh;
- create no Delivery;
- create no Reservation;
- change no stock.

### Released → Closed

Normal close requires no remaining fulfillment quantity according to the canonical quantity projection.

Short close explicitly moves approved remainder into `short_closed_base_quantity` first.

### Cancel

Allow direct Sales cancellation only when there is no non-cancelled Delivery execution requiring Logistics resolution and no completed Delivery.

## Acceptance tests

- Draft creation touches no stock.
- Confirm touches no stock/reservation.
- Release touches no stock/reservation/Delivery/Shipment.
- Confirmed lines cannot be changed through generic edit.
- Released lines cannot be changed through generic edit.
- short close cannot exceed remaining quantity.
- cancel cannot occur after a completed Delivery.

# 11. Phase 4 — Canonical Order quantity projection and partial fulfillment

## Problem

The current fulfillment service uses the full ordered quantity and blocks subsequent fulfillment when prior Delivery/Shipment records exist.

## 11.1 Create a canonical quantity service

Create:

- `app/Services/Sales/OrderFulfillmentQuantityService.php`

Return a per-OrderLine DTO containing at minimum:

```text
ordered_base
short_closed_base
planned_base
reserved_base
ready_base
dispatched_base
arrived_base
returned_base
invoiced_base
remaining_to_plan_base
```

### Source rules

**Ordered**
- `OrderLine.base_quantity`.

**Short-closed**
- `OrderLine.short_closed_base_quantity`.

**Planned**
- sum non-cancelled Delivery operation lines linked by `order_line_id`.

**Reserved / Ready**
- Delivery operations in the stages where active Inventory reservation exists / operation is Ready.

**Dispatched**
- Delivery operation lines whose Delivery `InventoryOperation` is `Done`.

**Arrived**
- dispatched Delivery lines whose linked Shipment is `Arrived`.

**Returned**
- posted Customer Return lines linked to the original Delivery lines.

**Invoiced**
- derive from Invoice lines/delivery links according to existing invoice document rules. Distinguish Draft invoice coverage from issued financial exposure if needed by the UI.

**Remaining to plan**

```text
ordered_base
- short_closed_base
- non_cancelled_planned_base
```

Do not subtract Customer Returns from normal remaining fulfillment. A return is a post-delivery event; replacement is a separate explicit business decision.

## 11.2 Preserve line provenance

A single variant may occur on multiple Order lines with different UOM/price provenance.

When planning a new Delivery:

1. calculate remaining base quantity per `order_line_id`;
2. allocate warehouse quantity by variant;
3. consume that allocation against remaining commercial lines in stable OrderLine order;
4. persist `order_line_id` on every Delivery line;
5. never allocate more than that OrderLine's remaining base quantity.

## 11.3 Concurrency

The planning transaction must lock, in deterministic order:

1. Order;
2. Order lines;
3. existing non-cancelled Delivery lines for the Order;
4. warehouse/stock/reservation rows used for the new plan.

After acquiring locks, recompute remaining quantity before writing.

## Acceptance tests

- Order 100 → plan 60 → second plan may plan only 40.
- two simultaneous planners cannot create 60 + 60 against remaining 100.
- cancelled Delivery quantity becomes plannable again.
- Done Delivery quantity never becomes plannable again.
- short-closed quantity never becomes plannable.
- duplicate variant lines preserve exact `order_line_id` provenance.

## 13.2 Planning sequence

Recommended sequence:

```text
Released Order
→ calculate remaining demand
→ suggest warehouse split
→ warehouse user adjusts
→ validate against current stock
→ create Delivery operation(s) in Draft
→ create Shipment record(s) as Planned
→ assign lot/serial evidence
→ user performs Reserve & Prepare

```

Do not call `markReady()` implicitly at commercial Order creation.

## 13.3 Shipment statuses

Extend `ShipmentStatus`:

```text
Planned
InTransit
Arrived
Cancelled
```

Semantics:

**Planned**
- Delivery exists but goods have not left warehouse.
- tracking/attachments may be prepared.
- never eligible for automatic arrival.

**InTransit**
- associated Delivery has been completed by Inventory;
- stock has left warehouse.

**Arrived**
- customer/admin/system arrival confirmation;
- warranty activation may occur.

**Cancelled**
- planned shipment cancelled before dispatch.

Add a unique database constraint on `shipments.inventory_operation_id` after reconciliation proves one Shipment per Delivery.

## 13.4 Reservation behavior

`Reserve & Prepare` calls the existing canonical `InventoryOperationService::markReady()`.

Preserve:

- row locking;
- available-stock checks;
- reservation creation;
- lot/serial validation;
- zero on-hand movement at Ready.

## Acceptance tests

- planned Delivery and Shipment touch no on-hand quantity;
- Shipment is `Planned`, never `InTransit`, while Delivery is Draft/Waiting/Ready;
- reservation reduces available quantity through canonical reservation behavior only;
- stale serial/lot assignment is rejected at prepare/dispatch validation;

# 14. Phase 7 — Dispatch integrity and Shipment transition

## Problem

Current code creates `ShipmentStatus::InTransit` immediately after `markReady()`, which is earlier than the physical stock movement.

## 14.1 New dispatch orchestration

Create:

- `app/Services/Logistics/OutboundDispatchService.php`

Responsibilities:

```php
dispatch(User $actor, InventoryOperation $delivery, array $shipmentData = []): Shipment
```

Transaction:

1. lock Delivery;
2. require `OperationType::Delivery`;
3. require Ready stage;
4. require linked Shipment in Planned state;
5. revalidate lot/serial/reservation invariants through canonical Inventory service;
6. call `InventoryOperationService::complete()`;
7. verify Delivery is Done;
8. transition Shipment `Planned → InTransit`;
9. synchronize tracking/attachments supplied at dispatch;
10. activity-log dispatch;
11. emit after-commit notification event.

The stock movement remains inside `InventoryOperationService`; `OutboundDispatchService` must not write stock directly.

## 14.2 Inventory UI wording

For a Delivery operation, the business action displayed to Logistics should be `Dispatch Goods`, even if the underlying canonical Inventory method remains `complete()`.

Do not expose an Inventory action suggesting the Shipment is in transit before this operation succeeds.

## 14.3 Arrival

`ShipmentService::confirmByAdmin/customer/system()` remains the arrival authority.

Guard arrival:

- Shipment must be `InTransit`;
- linked Delivery must be Done;
- repeated arrival confirmation must be idempotently rejected/ignored according to current policy.

Warranty activation remains after successful Arrival.

## 14.4 Automatic arrival

`eligibleForAutomaticArrival()` must only select `InTransit`, never Planned.

Prefer dispatch timestamp from linked Delivery `completed_at` for transit-age logic instead of Shipment `created_at`, because Planned shipment records may exist long before dispatch.

## Acceptance tests
